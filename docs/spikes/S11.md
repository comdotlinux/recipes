# Spike S11: alarm and storage behaviour of SQLite-backed Durable Objects

Date: 2026-11-24. Runtime: local workerd 1.20261123.1 (bundled by `@cloudflare/vitest-plugin` 1.9.2 and miniflare 5.20261123.1-beta), compatibility date 2026-11-23.

The tests live in `backend/test/spikes/s11-alarms.test.ts` and use the test-only object `backend/test/spikes/spike-do.ts`. They document platform behaviour, so they are not part of the default `bun run test` (a runtime change must not turn the product suite red). Run them on their own: `cd backend && bun run test:spikes`. If a workerd upgrade changes any behaviour, they fail.

## Summary

| Question | Local result | Plan impact |
|----------|--------------|-------------|
| (a) Does setting an alarm replace the pending one? | **Yes.** One slot per object | Alarm rule in 4.3 holds |
| (b) Is a thrown alarm handler retried? | **Yes.** About 2.3 s later, `isRetry = true`, `retryCount = 1` | Rule "handler never throws" in 4.3 stays: a throw re-runs every task in the handler |
| (c) Are writes made without an `await` right after `deleteAll()` committed together with it? | **No.** `deleteAll()` is not rolled back with them. An abort before the next `await` leaves the object wiped **without** the tombstone | **Plan 4.7 must change to the S11 fallback** (see below) |
| `deleteAll()`: drop tables or rows? | **Drops the tables.** Also clears the pending alarm | Re-creating `meta` and `tasks` is needed, as the plan says |
| (d) Does alarm-driven work finish after the client that started it disconnects? | **Yes.** Also, the cancelled request's own handler ran to its end | Jobs as alarm tasks hold; no Queues needed |

## (a) setAlarm replaces the pending alarm

Method: inside the object, `setAlarm(now + 60 s)`, then `setAlarm(now + 120 s)`, then `getAlarm()`. Then `runDurableObjectAlarm()` twice.

Result: `getAlarm()` returns the second time. The first `runDurableObjectAlarm()` runs the handler (returns `true`). The second returns `false` (no alarm left), and the handler ran exactly once. The first time was not kept as a separate alarm.

Local cannot prove: the same on a deployment, where alarms are stored by the Durable Object alarm service, not by the local workerd scheduler.

## (b) A thrown alarm handler is retried

Method: the handler logs `retryCount` and throws when `isRetry` is false. The alarm is set 10 ms ahead and the real local scheduler fires it (no `runDurableObjectAlarm`).

Result: two invocations. The first has `retryCount = 0`; the retry has `isRetry = true`, `retryCount = 1`. The test asserts a delay of at least 1.5 s; the first run measured 2265 ms.

Local cannot prove: the retry schedule on a deployment (https://developers.cloudflare.com/durable-objects/api/alarms/ documents exponential backoff starting at 2 s, up to 6 retries, for the most recent `setAlarm()` only), and whether the retry runs on the same instance.

## (c) deleteAll() and the writes after it

Method: four tests. Each seeds a `recipes` table with one row. The crash is `ctx.abort()` called synchronously, before any `await`.

1. Without an abort: `deleteAll()` is not awaited, then `CREATE TABLE IF NOT EXISTS meta` and `INSERT` of the tombstone row, then `await` of the `deleteAll()` promise. Result: only `meta` is left and the tombstone row is present. So `deleteAll()` applies before the later synchronous writes and does not wipe them.
2. Control: `DELETE FROM recipes` and `CREATE TABLE meta`, then abort. Result: both writes are rolled back (`recipes` is still present). Plain unawaited SQL writes are one atomic batch.
3. Finding: `deleteAll()` (not awaited), create `meta`, insert the tombstone, then abort. Result: **no tables at all, no tombstone**. The wipe is committed and the writes after it are rolled back. The plan's assumption ("such writes are committed together") is false locally.
4. Fallback: `transactionSync()` that runs `DROP TABLE` for each table in `sqlite_master` (excluding `sqlite_*` and `_cf_*`), creates `meta` and inserts the tombstone. With an abort right after it: the old `recipes` table is intact and there is no tombstone (nothing applied). Without an abort: only `meta` with the tombstone. The transaction is all-or-nothing in both cases.

Recommended plan change (4.7, final step). This is the fallback that the plan's S11 row already names. In one `transactionSync()`, drop every user table found in `sqlite_master` and create `meta` and `tasks`. Then write the tombstone row and its wipe task. After the transaction, call `setAlarm()` for the wipe task. `deleteAll()` is not used for the tombstone path. The object is never wiped without its tombstone. Note that this path does not reclaim internal storage the way `deleteAll()` does. When no tombstone is needed (the free import was not used and nothing was refunded), `deleteAll()` alone is still correct.

Also observed: after `await deleteAll()`, `getAlarm()` returns `null`, so `deleteAll()` clears the alarm here. This matches the documented behaviour for compatibility dates of 2026-02-24 or later (https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/, section `deleteAll`). The same page says `deleteAll()` on SQLite-backed objects "removes the entire contents" of the database and is atomic on its own; it says nothing about atomicity with later writes. The plan calls `deleteAlarm()` explicitly anyway; keep that, because it costs nothing.

Local cannot prove: crash behaviour on a deployment. `ctx.abort()` only models a crash of the isolate before the output gate opens. It does not model a machine failure during the commit or a replica failover, and production `deleteAll()` on SQLite-backed objects may be implemented differently from local workerd. Re-check test 3 on staging before relying on any change in this behaviour.

## (d) Alarm-driven work after the client disconnects

Method: the client calls the object's `fetch()` with an `AbortSignal`. The handler logs `request-start`, sets an alarm for now in mode `work`, then waits 1.5 s and logs `request-end`. The client aborts as soon as `request-start` is visible. The alarm handler waits 300 ms and logs `work-done`.

Result: the client's call rejects with an error. The test waits for, and asserts, the order of events: `request-start, alarm, work-done, request-end`. The alarm work finished after the client disconnected, and the cancelled request's handler also ran to its end.

Local cannot prove: that a deployed object keeps running the request handler after a client disconnect. Do not rely on it: keep paid work in alarm tasks, as the plan does. Also not proven: the disconnect of a real mobile client through the Worker and the edge (here the client is the test calling the object stub directly), and eviction of an idle object between alarm runs on a deployment.
