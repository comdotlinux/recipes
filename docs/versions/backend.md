## RevenueCat (M3, checked 2026-11-25)

Read through Context7 (library ids `/websites/revenuecat_api-v1`, `/websites/revenuecat_api-v2`, `/websites/revenuecat`), which indexes the pages below.

| Use | Endpoint and version | Key | Source | What the source states |
|-----|----------------------|-----|--------|------------------------|
| Entitlement refresh (`src/billing/revenuecat.ts`) | `GET https://api.revenuecat.com/v1/subscribers/{app_user_id}`, REST API v1 | secret API key (`sk_...`) as `Authorization: Bearer <key>`; Worker secret `REVENUECAT_API_KEY` | https://www.revenuecat.com/docs/api-v1/customers.md, https://www.revenuecat.com/docs/api-v1 | returns `subscriber.entitlements.<id>` with `expires_date`, `grace_period_expires_date`, `product_identifier`, `purchase_date` (expired entitlements included), and `subscriber.subscriptions.<product>` with `refunded_at`; 200 found, 201 created: the call creates a customer that does not exist yet; `X-Platform` must not be sent for informational reads |
| Not used: v2 active entitlements | `GET https://api.revenuecat.com/v2/projects/{project_id}/customers/{customer_id}/active_entitlements` | v2 secret key with `customer_information:customers:read`; v1 keys do not work with v2 | https://www.revenuecat.com/docs/api-v2/customer/resources | items have only `entitlement_id` (RevenueCat's internal id) and `expires_at` (ms); no grace-period date and no product, so v1 is used |
| Account deletion (M6, recorded only) | `DELETE https://api.revenuecat.com/v2/projects/{project_id}/customers/{customer_id}`, REST API v2 | v2 secret key with `customer_information:customers:read_write` | https://www.revenuecat.com/docs/api-v2/customer | deletion is queued; after 200, a v2 "get customer" answering 404 confirms it. Needs the project id and a v2 key, which the v1 key above cannot replace |

Webhooks (https://www.revenuecat.com/docs/integrations/webhooks, https://www.revenuecat.com/docs/integrations/webhooks/event-types-and-fields, https://www.revenuecat.com/docs/integrations/webhooks/sample-events):
- `POST` with a JSON body `{ "api_version": "1.0", "event": { ... } }`; `event.type`, `event.id`, `event.app_user_id`, `event.original_app_user_id`, `event.aliases`, `event.entitlement_ids`, `event.product_id`, `event.expiration_at_ms`, `event.environment` (`SANDBOX` or `PRODUCTION`), price fields.
- Types: `INITIAL_PURCHASE`, `RENEWAL`, `CANCELLATION`, `UNCANCELLATION`, `NON_RENEWING_PURCHASE`, `SUBSCRIPTION_PAUSED`, `EXPIRATION`, `BILLING_ISSUE`, `PRODUCT_CHANGE`, `TRANSFER`, `SUBSCRIPTION_EXTENDED`, `REFUND_REVERSED`, `INVOICE_ISSUANCE`, plus `TEST` from the dashboard; new types and fields may be added without a version change.
- `TRANSFER` carries `transferred_from` and `transferred_to` (arrays of app user ids); the webhook is sent only for the destination user.
- A refund arrives as `CANCELLATION` with `cancel_reason` `CUSTOMER_SUPPORT` (the web-billing page names the field `cancellation_reason`; the code reads neither, it re-reads the REST record).
- Authorisation: an "Authorization header value" set in the dashboard is sent unchanged in every request. HMAC signing with `X-RevenueCat-Webhook-Signature` is recommended as a stronger option; not used yet.
- Any answer other than 200 is a failure; RevenueCat retries up to 5 times (about 2.5, 5, 10, 20, 40 minutes) and recommends answering fast and processing later; duplicates can occur.

UNVERIFIED until the owner connects the RevenueCat project: real responses of the v1 endpoint for a sandbox purchase (field presence, how a refund shows in `expires_date` and `refunded_at`), the exact header RevenueCat sends, and the restore behaviour setting named in plan 4.6.
