## RevenueCat (M3, checked 2026-11-25)

Read through Context7 (library ids `/websites/revenuecat_api-v1`, `/websites/revenuecat_api-v2`, `/websites/revenuecat`), which indexes the pages below.

| Use | Endpoint and version | Key | Source | What the source states |
|-----|----------------------|-----|--------|------------------------|
| Entitlement refresh (`src/billing/revenuecat.ts`) | `GET https://api.revenuecat.com/v1/subscribers/{app_user_id}`, REST API v1 | secret API key (`sk_...`) as `Authorization: Bearer <key>`; Worker secret `REVENUECAT_API_KEY` | https://www.revenuecat.com/docs/api-v1/customers.md, https://www.revenuecat.com/docs/api-v1 | returns `subscriber.entitlements.<id>` with `expires_date`, `grace_period_expires_date`, `product_identifier`, `purchase_date` (expired entitlements included), and `subscriber.subscriptions.<product>` with `refunded_at`; 200 found, 201 created: the call creates a customer that does not exist yet; `X-Platform` must not be sent for informational reads |
| Not used: v2 active entitlements | `GET https://api.revenuecat.com/v2/projects/{project_id}/customers/{customer_id}/active_entitlements` | v2 secret key with `customer_information:customers:read`; v1 keys do not work with v2 | https://www.revenuecat.com/docs/api-v2/customer/resources | items have only `entitlement_id` (RevenueCat's internal id) and `expires_at` (ms); no grace-period date and no product, so v1 is used |
| Account deletion (M6, recorded only) | `DELETE https://api.revenuecat.com/v2/projects/{project_id}/customers/{customer_id}`, REST API v2 | v2 secret key with `customer_information:customers:read_write` | https://www.revenuecat.com/docs/api-v2/customer | deletion is queued; after 200, a v2 "get customer" answering 404 confirms it. Needs the project id and a v2 key, which the v1 key above cannot replace |

Webhooks (https://www.revenuecat.com/docs/integrations/webhooks, https://www.revenuecat.com/docs/integrations/webhooks/event-types-and-fields, https://www.revenuecat.com/docs/integrations/webhooks/sample-events):
- `POST` with a JSON body `{ "api_version": "1.0", "event": { ... } }`; `event.type`, `event.id`, `event.app_user_id`, `event.original_app_user_id`, `event.aliases`, `event.entitlement_ids`, `event.product_id`, `event.expiration_at_ms`, `event.environment` (`SANDBOX` or `PRODUCTION`), price fields.
- Types: `INITIAL_PURCHASE`, `RENEWAL`, `CANCELLATION`, `UNCANCELLATION`, `NON_RENEWING_PURCHASE`, `SUBSCRIPTION_PAUSED`, `EXPIRATION`, `BILLING_ISSUE`, `PRODUCT_CHANGE`, `TRANSFER`, `SUBSCRIPTION_EXTENDED`, `REFUND_REVERSED`, `INVOICE_ISSUANCE`, plus `TEST` from the dashboard; new types and fields may be added without a version change.
- `TRANSFER` carries `transferred_from` and `transferred_to` (arrays of app user ids); the webhook is sent only for the destination user.
- A refund arrives as `CANCELLATION` with `cancel_reason` `CUSTOMER_SUPPORT` (the web-billing page names the field `cancellation_reason`; the code reads neither, it re-reads the REST record).
- Authorisation: an "Authorization header value" set in the dashboard is sent unchanged in every request. HMAC signing with `X-RevenueCat-Webhook-Signature` is recommended as a stronger option; not used yet.
- Any answer other than 200 is a failure; RevenueCat retries up to 5 times (about 2.5, 5, 10, 20, 40 minutes) and recommends answering fast and processing later; duplicates can occur.

Decisions about the mapping (security review M3, 2026-11-25):
- Restore behaviour: the RevenueCat dashboard must be set to "keep with original App User ID" (owner action), so one store subscription cannot feed several accounts' monthly quotas; if it is set to transfer anyway, a `TRANSFER` refreshes both accounts and the old one loses the entitlement at its refresh, so two accounts are never active at once after both refreshes ran.
- `is_sandbox` is ignored on purpose: Apple's App Review and TestFlight testers buy in the store sandbox against the production build, so production must honour sandbox purchases or review fails. Residual, accepted: store testers (only people the owner adds as sandbox or TestFlight testers) get Pro without paying.
- Non-subscription (lifetime) purchases are not mapped, because no such product exists; only the `recipes_pro` entitlement of the `monthly` subscription counts.
- Freshness: an answer is stored only if no refresh that started later stored one first (`entitlement_at`); an active record is re-read at most once a day even without a webhook, so a refund whose webhook was lost ends access within a day.

UNVERIFIED until the owner connects the RevenueCat project: real responses of the v1 endpoint for a sandbox purchase (field presence, how a refund shows in `expires_date` and `refunded_at`), the exact header RevenueCat sends, and the restore behaviour setting named in plan 4.6.

## Browser Run, PDF rendering (M5, checked 2026-11-25)

The plan's "Browser Run" is the current product name (formerly Browser Rendering); docs at `https://developers.cloudflare.com/browser-run/`, read through Context7 (library id `/websites/developers_cloudflare_browser-run`) on 2026-11-25, and the generated runtime types (`BrowserRun`, `BrowserRunPDFOptions` in `backend/worker-configuration.d.ts`, workerd 1.20261123.1).

| Fact | Value | Source |
|------|-------|--------|
| Binding | `"browser": { "binding": "BROWSER" }` in the Wrangler config; type `BrowserRun` | https://developers.cloudflare.com/browser-run/get-started/ |
| Call | `env.BROWSER.quickAction("pdf", { html, ... })` returns a `Response`: 200 `application/pdf`, or JSON error 400, 422, 429, 500, 503; header `X-Browser-Ms-Used`. No API token with the binding. Needs compatibility date 2026-03-24 or later (ours: 2026-11-23) | https://developers.cloudflare.com/browser-run/quick-actions/pdf-endpoint/, runtime types |
| JavaScript off | `setJavaScriptEnabled: false` (shared Quick Action option; the snapshot docs use it with `html` input) | https://developers.cloudflare.com/browser-run/quick-actions/snapshot/, runtime types |
| Blocking requests | `rejectRequestPattern` / `allowRequestPattern` (regex strings; the docs' example is `"/^.*\\.(css)"`), `rejectResourceTypes`; `cacheTTL` (default 5 s, 0 disables) | pdf-endpoint page, runtime types |
| Limits, Workers Paid | Quick Actions 30 requests per second per account; browser timeout 60 s; `PDFOptions.timeout` default 30 s, max 5 min; `goToOptions.timeout` max 60 s | https://developers.cloudflare.com/browser-run/limits/, https://developers.cloudflare.com/browser-run/reference/timeouts/ |
| Pricing | Quick Actions are charged for browser hours only. Workers Free: 10 minutes per day. Workers Paid: 10 hours per month included, then $0.09 per hour | https://developers.cloudflare.com/browser-run/pricing/ |

Cost finding and decision: a render of one inline recipe page should take about 1 to 3 seconds of browser time (estimate; `X-Browser-Ms-Used` gives the real figure once the owner runs it). The 10 included hours are about 12,000 to 36,000 renders a month for the whole account; beyond that a 2-second render costs about $0.00005 (5 US cents per 1,000 PDFs). One user at the cap of 20 a day uses at most about 20 minutes a month. That is not real money per call, so PDF stays free for every signed-in user, bounded by the per-user cap of 20 a day and the global `RL_GLOBAL` key `pdf`. On the Workers Free plan the 10 minutes a day would be about 300 renders a day for everyone; the production account is expected on Workers Paid (Durable Objects billing), which the owner confirms when logging in.

Safety of the render (`backend/src/pdf.ts`): every recipe field is HTML-escaped; pictures are data URIs read from the user's own storage; the page carries the CSP `default-src 'none'; img-src data:; font-src data:; style-src 'unsafe-inline'`; the call passes `setJavaScriptEnabled: false`, `cacheTTL: 0` and `rejectRequestPattern: ["/^(https?|wss?|ftp):/"]`. Session guardrails (`allowedDomains: []`) exist only for Browser Sessions, not for Quick Actions.
